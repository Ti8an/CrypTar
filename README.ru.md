# CrypTar

**CrypTar** — Bash-инструмент для архивирования, GPG-шифрования и отправки резервных копий на удалённые серверы через SSH и в облачные хранилища (Google Drive, Яндекс Диск).

---

## Установка

Клонируйте репозиторий:
```bash
git clone https://github.com/Ti8an/CrypTar.git
```

Перейдите в директорию проекта:
```bash
cd CrypTar
```

Сделайте установщик исполняемым:
```bash
chmod +x install.sh
```

Запустите установщик:
```bash
./install.sh
```

Установщик проверяет и при необходимости устанавливает: `tar`, `gnupg`, `openssh-client`, `curl`, `jq`, `sshpass`.

> **Примечание:** при установке `sshpass` выводится предупреждение — предпочтительна аутентификация по SSH-ключу.

Повторный запуск установщика безопасен: он заменяет только `crypTar` и библиотеку `src/`, сохраняет `~/.config/cryptar/` и ключи и не дублирует строки `PATH`. Для последующих обновлений используйте `crypTar --update` (см. [Обновление](#обновление)).

`curl` и `jq` нужны только командам `--cloud`, `--update` и `--check-update`; если их нет, эти команды завершаются с ошибкой и подсказкой, какой пакет установить. Установщик никогда не запрашивает облачные/OAuth-учётные данные.

## Команды

| Команда | Описание |
|---|---|
| `crypTar <путь>` | Архивировать и зашифровать файл или папку |
| `crypTar -s <путь>` | Архивировать, зашифровать и отправить на сервер |
| `crypTar -d <файл.tar.gz.gpg>` | Расшифровать и распаковать архив |
| `crypTar --server list` | Показать список настроенных серверов |
| `crypTar --server add` | Добавить новый сервер (интерактивный мастер) |
| `crypTar --server remove` | Удалить сервер |
| `crypTar --server push-key` | Отправить GPG-ключ на сервер |
| `crypTar --server set-key` | Сменить ключ шифрования конфигов (серверы и облака) |
| `crypTar --cloud add` | Добавить облачное подключение (интерактивный мастер) |
| `crypTar --cloud list [--check]` | Список облачных подключений (`--check` — живая проверка каждого) |
| `crypTar --cloud remove [имя\|номер]` | Удалить облачное подключение (только локальный конфиг) |
| `crypTar --cloud test [имя\|номер\|--all]` | Проверить авторизацию и доступ к папке назначения |
| `crypTar --cloud send [--to имя1,имя2] <путь>` | Загрузить зашифрованный архив или архивировать + зашифровать + загрузить |
| `crypTar --cloud reauth [имя\|номер]` | Повторная авторизация подключения (истёкший/отозванный токен) |
| `crypTar --check-update` | Проверить наличие нового стабильного релиза (ничего не меняет) |
| `crypTar --update [--yes]` | Установить последний стабильный релиз (`--yes` — без подтверждения) |
| `crypTar --version` | Показать версию |
| `crypTar -h \| --help` | Показать справку |

## Примеры использования

Зашифровать папку:
```bash
crypTar ~/projects/myApp
```
→ `myApp_25_05_2026_14_30_00.tar.gz.gpg`

Расшифровать:
```bash
crypTar -d myApp_25_05_2026_14_30_00.tar.gz.gpg
```

Зашифровать и сразу отправить на сервер:
```bash
crypTar -s ~/projects/myApp
```

Добавить удалённый сервер:
```bash
crypTar --server add
```

Посмотреть список серверов:
```bash
crypTar --server list
```

Отправить свой GPG-ключ на сервер (для расшифровки там):
```bash
crypTar --server push-key
```

Сменить GPG-ключ шифрования конфигов серверов и облаков:
```bash
crypTar --server set-key
```

Архивировать, зашифровать и загрузить сразу в два облачных аккаунта:
```bash
crypTar --cloud send --to google-work,yandex-backup ~/projects/myApp
```

## Облачные хранилища (Google Drive, Яндекс Диск)

CrypTar загружает зашифрованные архивы в любое количество облачных **подключений**. Подключение — это один авторизованный аккаунт одного провайдера плюс папка назначения; оно идентифицируется уникальным именем, которое вы задаёте. Поэтому несколько аккаунтов одного провайдера работают одновременно:

| ID | Имя | Провайдер | Аккаунт |
|---|---|---|---|
| 1 | google-work | Google Drive | work@example.com |
| 2 | google-personal | Google Drive | me@gmail.com |
| 3 | yandex-backup | Yandex Disk | my-login |

За пределы машины уходят только уже зашифрованные архивы `.gpg`.

### Как устроена авторизация

Оба провайдера используют официальный **OAuth 2.0 device authorization flow** (вход по коду устройства): CrypTar показывает адрес и короткий код, вы открываете адрес на любом устройстве (телефон, ноутбук), входите в аккаунт и разрешаете доступ. CrypTar никогда не видит пароль аккаунта, не требует локального веб-сервера и redirect URI и работает по SSH на серверах без графики.

Для каждого провайдера нужно собственное OAuth-приложение (Client ID + Client secret). Оно создаётся один раз и подходит для всех аккаунтов этого провайдера.

### Google Drive: настройка OAuth

1. Откройте [Google Cloud Console](https://console.cloud.google.com/) и создайте (или выберите) проект.
2. **APIs & Services → Library** → включите **Google Drive API**.
3. **Google Auth Platform / OAuth consent screen**: тип пользователей *External*, укажите имя приложения и контактный e-mail, добавьте scope `https://www.googleapis.com/auth/drive.file`.
   Пока приложение в статусе *Testing*, добавьте каждый подключаемый Google-аккаунт в **Test users**.
4. **Credentials → Create credentials → OAuth client ID** → тип приложения **TVs and Limited Input devices**. Скопируйте **Client ID** и **Client secret**.
5. Выполните `crypTar --cloud add`, выберите *Google Drive* и введите Client ID / secret.

Примечания:
- CrypTar запрашивает только scope `drive.file`: он видит и изменяет **только файлы и папки, созданные им самим**, — но не остальной Диск.
- Клиент для device flow не использует redirect URI — настраивать его не нужно.
- У приложений в статусе *Testing* Google аннулирует refresh-токены через 7 дней. Для долгосрочных автоматических бэкапов переведите приложение в статус *In production* (`drive.file` — не чувствительный scope) или выполняйте `crypTar --cloud reauth <имя>` по истечении токена.

### Яндекс Диск: настройка OAuth

1. Откройте [oauth.yandex.ru](https://oauth.yandex.ru/client/new) и создайте приложение.
2. В разделе доступа к данным добавьте права REST API Яндекс Диска:
   - `cloud_api:disk.write` — создание папок и загрузка файлов,
   - `cloud_api:disk.read` — проверка, существует ли файл / завершилась ли загрузка,
   - `cloud_api:disk.info` — логин аккаунта и свободное место.

   Либо выдайте только `cloud_api:disk.app_folder` и используйте папку вида `app:/CrypTar` (папка приложения).
3. Если форма требует платформу и Redirect URI, выберите *Веб-сервисы* и укажите `https://oauth.yandex.ru/verification_code` — device-code flow CrypTar его не использует.
4. Скопируйте **ClientID** и **Client secret** и введите их в `crypTar --cloud add` (выберите *Yandex Disk*).

### Как передать данные OAuth-клиента

Мастер `add` берёт Client ID / secret в таком порядке:
1. переменные окружения `CRYPTAR_GDRIVE_CLIENT_ID` / `CRYPTAR_GDRIVE_CLIENT_SECRET` или `CRYPTAR_YADISK_CLIENT_ID` / `CRYPTAR_YADISK_CLIENT_SECRET`;
2. существующее подключение того же провайдера (с подтверждением);
3. интерактивный ввод (секрет не отображается).

Затем они сохраняются в зашифрованном облачном конфиге вместе с токенами. Без Client ID и secret мастер завершается с ошибкой настройки — ничего не сохраняется.

### Добавление подключений

```bash
crypTar --cloud add
```

Мастер:
1. спрашивает провайдера;
2. спрашивает уникальное имя подключения — 1–64 символа `A-Z a-z 0-9 _ -`, начинается с буквы или цифры, не только цифры (числа зарезервированы под номера в списке). Существующее имя никогда не перезаписывается;
3. получает данные OAuth-клиента (см. выше);
4. выполняет авторизацию по коду устройства и проверяет доступ к аккаунту;
5. спрашивает папку назначения (по умолчанию `CrypTar` для Google Drive, `/CrypTar` для Яндекс Диска) и при необходимости создаёт её;
6. сохраняет подключение.

Запустите мастер ещё раз с другим именем, чтобы подключить второй аккаунт того же провайдера, например `google-work` и `google-personal`.

### Список, проверка, удаление

```bash
crypTar --cloud list            # статус «configured»: ничего не проверялось
crypTar --cloud list --check    # живая проверка: OK / AUTH ERROR / NETWORK ERROR / ...
crypTar --cloud test google-work
crypTar --cloud test 2          # по номеру из списка
crypTar --cloud test --all
crypTar --cloud test            # интерактивно: один или несколько («1,3», «1-3», «all»)
crypTar --cloud remove yandex-backup
crypTar --cloud remove 3
crypTar --cloud remove          # интерактивно
crypTar --cloud reauth google-work
```

Имена — постоянные идентификаторы; номера (колонка `ID` в `list`) — для удобства и меняются при добавлении/удалении подключений. `remove` запрашивает подтверждение и удаляет **только** локальную запись подключения и её токены — в облаке ничего не удаляется. Чтобы отозвать доступ CrypTar, используйте [разрешения аккаунта Google](https://myaccount.google.com/permissions) или раздел приложений в настройках безопасности Яндекс ID.

`test` проверяет авторизацию (обновляя токен), показывает аккаунт и свободное место и проверяет (при необходимости создаёт) папку назначения.

### Загрузка

Загрузить существующий зашифрованный архив (загружается как есть, повторно не шифруется):
```bash
crypTar --cloud send --to google-work backup_12_10_2026_20_00_00.tar.gz.gpg
```

Архивировать + зашифровать + загрузить за один шаг (тот же код архивирования/шифрования и те же имена файлов, что у `crypTar <путь>`):
```bash
crypTar --cloud send --to google-work,yandex-backup ~/Documents
```

Несколько назначений: через запятую и/или повторным `--to` (`--to a --to=b`). Без `--to` показывается интерактивное меню множественного выбора.

Как определяется тип входного пути:
- обычный файл `*.gpg`, заголовок которого — зашифрованное OpenPGP-сообщение → загружается напрямую;
- файл `*.gpg`, который **не** является OpenPGP-шифротекстом → отклоняется (переименуйте его, если нужно архивировать);
- любой другой файл или каталог → сначала архивируется и шифруется вашим GPG-ключом.

Поведение:
- каждое имя в `--to` должно точно совпадать с подключением; при неизвестном имени команда завершается до архивирования и загрузки;
- один и тот же локальный файл загружается во все назначения (без лишних копий); ошибка в одном назначении не останавливает остальные; в конце выводится таблица результатов по каждому назначению;
- архивы, созданные `send`, следуют соглашению `crypTar -s`: если **все** загрузки успешны, предлагается удалить локальную копию; если хоть одна не удалась, архив всегда сохраняется в текущей директории. Переданный вами архив никогда не изменяется и не удаляется;
- **конфликт имён**: существующий файл в облаке никогда не перезаписывается — загрузка получает свободное имя с числовым суффиксом (`name-1.tar.gz.gpg`, `name-2.tar.gz.gpg`, …).

Коды выхода `send`: `0` — все загрузки успешны, `3` — часть не удалась, `1` — все не удались или неверные входные данные. `test` для одного подключения возвращает конкретный код ошибки (`10` авторизация, `11` права, `12` сеть, `13` лимит запросов, `14` квота, `16` конфигурация).

### Папки назначения

- **Google Drive** адресует папки по ID. CrypTar хранит введённый путь (например, `CrypTar` или `Backups/CrypTar`) и найденный ID папки; если папку удалили или переместили в корзину, при следующей загрузке она будет найдена или создана заново автоматически.
- **Яндекс Диск** адресует ресурсы по пути: `/CrypTar`, `disk:/Backups/CrypTar` или `app:/CrypTar` (папка приложения). Отсутствующие папки создаются по уровням.

### Надёжность

- Временные ошибки (сеть, тайм-ауты, HTTP 429/5xx, 403 rate limit Google) повторяются до 4 раз с экспоненциальной задержкой (1, 2, 4, 8 с) с учётом `Retry-After`. Постоянные ошибки (авторизация, права, квота, неверный запрос) не повторяются. Число попыток задаётся `CRYPTAR_CLOUD_MAX_RETRIES`.
- Загрузка в Google Drive идёт через **resumable upload session**: после обрыва CrypTar спрашивает у сервера, сколько байт получено, и продолжает с этого места (истёкшая сессия перезапускается один раз).
- Яндекс Диск: при обрыве CrypTar сначала проверяет, не появился ли файл уже (тот же размер), и только потом загружает заново по новой ссылке. Ответ `202 Accepted` отслеживается до сохранения файла.
- Создание папки в Google Drive не повторяется вслепую: после неудачного создания CrypTar сначала ищет папку.

### Где хранятся конфигурация и учётные данные

| Файл | Содержимое |
|---|---|
| `~/.config/cryptar/clouds.conf.gpg` | Облачные подключения: провайдер, аккаунт, папка, ID папки, Client ID/secret, токены — зашифровано GPG, `chmod 600` |
| `~/.config/cryptar/servers.conf.gpg` | SSH-серверы (без изменений) |
| `~/.config/cryptar/.gpg_key_id` | ID GPG-ключа, которым шифруются оба конфига |

Облачный конфиг использует тот же формат зашифрованного INI, GPG-ключ, файл блокировки и атомарную запись (`*.tmp` + переименование), что и конфиг серверов, но это отдельный файл, поэтому облачные подключения не появляются в командах `--server`. `crypTar --server set-key` перешифровывает оба файла.

Хранимые токены: Google — только refresh-токен (access-токен живёт в памяти в течение одного запуска); Яндекс — access-токен, refresh-токен и срок действия (обновляется за сутки до истечения).

### Решение проблем

Код выхода `crypTar --cloud test <имя>` или статус в `list --check` указывает на причину.

| Симптом (код выхода / статус) | Решение |
|---|---|
| Не найдены `curl` / `jq` (код 16) | `sudo apt-get install curl jq` или повторно запустите `install.sh` |
| Не задан OAuth-клиент (код 16) | Создайте OAuth-приложение (см. выше) и введите Client ID/secret или задайте переменные `CRYPTAR_*_CLIENT_ID/SECRET` |
| `invalid_client` — ошибка конфигурации (код 16) | Неверный Client ID/secret или клиент Google не типа *TVs and Limited Input devices* |
| Ошибка авторизации (код 10, `AUTH ERROR`) | Токен истёк или отозван: `crypTar --cloud reauth <имя>` (у приложений Google в статусе *Testing* токены живут 7 дней) |
| Недостаточно прав (код 11, `NO ACCESS`) | Не хватает scope/прав: проверьте права приложения, затем `reauth` |
| Недостаточно места (код 14, `QUOTA FULL`) | Освободите место или выберите другое подключение |
| Файл превышает лимит провайдера (код 18) | Яндекс Диск: 1 ГБ на файл (50 ГБ с Яндекс 360) |
| Лимит запросов (код 13, `RATE LIMITED`) | Подождите несколько минут и повторите |
| Сетевая ошибка или тайм-аут (код 12, `NETWORK ERROR`) | Проверьте сеть / прокси; загрузка по возможности продолжится |
| Не удаётся расшифровать `clouds.conf.gpg` | В keyring нет секретного GPG-ключа, которым зашифрован конфиг |

### Ограничения

- Первая авторизация каждого подключения интерактивна (нужен браузер на любом устройстве); последующие запуски — без участия пользователя.
- Загрузка в несколько назначений выполняется последовательно.
- Нет скачивания/восстановления, просмотра файлов в облаке и автоочистки старых копий — используйте веб-интерфейс провайдера.
- Scope `drive.file` в Google Drive: папка, созданная вручную в Диске, CrypTar не видна; CrypTar создаёт свою папку (возможно, с тем же именем).
- У Яндекс Диска нет API докачки: прерванная загрузка начинается заново (после проверки, что она не завершилась).
- Проверка конфликтов имён в Google Drive не защищает от *одновременных* загрузок с одинаковым именем (Диск допускает одинаковые имена; перезаписи не происходит никогда).

### Ручной интеграционный тест (необязательно)

Автотесты подменяют весь HTTP-трафик. Для проверки на реальных сервисах используйте **отдельные тестовые аккаунты**:

1. Создайте OAuth-приложения, как описано выше (Google: добавьте тестовый аккаунт в test users).
2. `crypTar --cloud add` → Google Drive → `gtest1`; повторите со вторым Google-аккаунтом → `gtest2`; добавьте Яндекс → `ytest`.
3. `crypTar --cloud list --check` → везде `OK`.
4. `crypTar --cloud send --to gtest1,gtest2,ytest /etc/hostname` → три строки `OK`; архив появился в каждой папке назначения.
5. Дважды выполните `send` с одним и тем же готовым архивом → вторая загрузка получает суффикс `-1`.
6. Удалите папку назначения в веб-интерфейсе Диска → `crypTar --cloud test gtest1` создаёт её заново.
7. Отзовите доступ (страница разрешений Google) → `crypTar --cloud test gtest1` сообщает об ошибке авторизации → `crypTar --cloud reauth gtest1` восстанавливает доступ.
8. Скачайте один из загруженных архивов и выполните `crypTar -d` → содержимое совпадает.
9. `crypTar --cloud remove gtest2` → исчезает только локальная запись; файлы остаются в Диске.

## Обновление

```bash
crypTar --check-update     # показать установленную и последнюю стабильную версию, ничего не меняя
crypTar --update           # загрузить, проверить и установить последний стабильный релиз
crypTar --update --yes     # то же без запроса подтверждения (cron, автоматизация)
```

Удалять старую версию и заново клонировать репозиторий не нужно; Git не требуется.

### Как это работает

1. CrypTar запрашивает у GitHub API **последний опубликованный стабильный релиз** `Ti8an/CrypTar` (`/releases/latest`). Черновики и pre-release никогда не устанавливаются; ветка `main` и произвольные коммиты не используются как источник обновлений.
2. Версии сравниваются по правилам старшинства SemVer. Если установлена та же версия, ничего не происходит. Если установленная версия новее последнего релиза (например, сборка для разработки), тоже ничего не происходит: автоматического понижения версии нет.
3. Релиз загружается от имени текущего пользователя в закрытый временный каталог (права 700). Разрешён только HTTPS, в том числе при перенаправлениях; размер загрузки ограничен.
4. До замены каких-либо файлов загрузка проверяется:
   - подписанный манифест и контрольная сумма, если они настроены (см. [Подлинность релизов](#подлинность-релизов));
   - целостность gzip;
   - состав архива: только обычные файлы и каталоги внутри одного корневого каталога; абсолютные пути, `..`, символические ссылки и спецфайлы отклоняются;
   - структура проекта и совпадение `VERSION` с тегом релиза;
   - `bash -n` для каждого скрипта.
5. Установка выполняется тем же кодом, что и в `install.sh` (`src/install/core.sh`):
   - рядом с целевым каталогом готовится и повторно проверяется копия;
   - подменяется `src/`, а `crypTar` заменяется атомарным переименованием;
   - запускается `crypTar --version`.

   Если любой шаг не удался, восстанавливается предыдущая версия.
6. Временные файлы удаляются в любом случае, в том числе при Ctrl-C.

### Что обновление никогда не затрагивает

`~/.config/cryptar/` (конфигурация серверов и облаков), GPG-ключи и keyring, SSH-ключи, архивы и резервные копии, файлы настройки оболочки и `PATH`, а также любые другие файлы рядом с установкой. Заменяются только `<bin>/crypTar` и `<lib>/src/`. Обновление никогда не создаёт GPG-ключи и не запускает загруженный `install.sh`.

### Пользовательская и системная установка

| Установка | Пути | Обновление |
|---|---|---|
| Пользовательская | `~/.local/bin/crypTar`, `~/.local/lib/cryptar/src` | от пользователя, без `sudo` |
| Системная | `/usr/local/bin/crypTar`, `/usr/local/lib/cryptar/src` | напрямую от root или от пользователя через `sudo` |

Если системную установку обновляет обычный пользователь, загрузка и проверка выполняются без повышенных прав. `sudo` запрашивается **только на шаге замены файлов**. Этот шаг выполняет уже установленная (доверенная) копия `src/install/core.sh`, а не код из загрузки; она копирует проверенное дерево в собственный промежуточный каталог и проверяет его повторно. Если `sudo` недоступен, запустите `crypTar --update` от root.

Каталог установки определяется по запущенному `crypTar` (установщик встраивает в него `SRC_DIR`). Запуск `--update` из рабочей копии Git отклоняется; используйте там `git pull`.

> В установках, сделанных до появления `--update`, этой команды нет. Один раз запустите `install.sh` из свежего клона (конфигурация и ключи сохраняются), дальше используйте `crypTar --update`.

### Ошибки

Во всех случаях ниже установленная версия остаётся без изменений.

| Ситуация | Сообщение | Код выхода |
|---|---|---|
| Нет сети, ошибка DNS или TLS, таймаут | «GitHub недоступен …» | 2 |
| Лимит запросов GitHub API (60 в час без токена) | время, когда лимит сбросится | 2 |
| GitHub отвечает 5xx | повторите позже | 2 |
| Нет опубликованных стабильных релизов | — | 1 |
| Некорректные метаданные, тег не в формате SemVer, последний релиз — черновик или pre-release | — | 1 |
| Ошибка загрузки, повреждённый или неожиданный архив, несовпадение версии, неверная подпись или контрольная сумма | — | 1 |
| Нет прав на запись и нет `sudo`; `sudo` отклонён | — | 3 / 1 |

`--check-update` завершается с кодом 0, если сама проверка прошла успешно, независимо от того, есть ли обновление.

### Подлинность релизов

Есть два режима:

- **Подписанные артефакты (рекомендуется).** Релиз содержит `cryptar-<версия>.tar.gz`, `SHA256SUMS` и `SHA256SUMS.asc`. Подпись проверяется во временном `GNUPGHOME` по ключу, закреплённому в *установленной* копии: `src/keys/release-signing-key.asc`. Keyring пользователя не используется и не изменяется. Если в установке есть закреплённый ключ, релизы без подписи отклоняются; тихого перехода на слабый режим нет.
- **Ключ не закреплён (текущее состояние репозитория).** Если у релиза есть подписанные артефакты, проверяется `SHA256SUMS`, но он получен из того же источника, что и архив, поэтому подтверждает только **целостность, а не подлинность**. Иначе используется архив исходников тега от GitHub. В обоих случаях подлинность обеспечивают только HTTPS и защищённость аккаунта и репозитория GitHub. CrypTar предупреждает об этом при каждом обновлении.

Чтобы включить проверку подписи, добавьте в репозиторий открытый ключ сопровождающего в формате ASCII-armor как `src/keys/release-signing-key.asc` и с этого момента публикуйте подписанные артефакты. Ключ попадает к пользователям при обычной установке или обновлении; с этого момента ему доверяют (trust on first use).

### Публикация релиза (для разработчика)

1. Обновите `VERSION` (формат `MAJOR.MINOR.PATCH-N`, где `N` — растущий номер релиза), закоммитьте и влейте в `main`.
2. Создайте тег `v<VERSION>`. Он должен в точности совпадать с `VERSION`, например `v1.4.1-5`:
   ```bash
   git tag v1.4.1-5 && git push origin v1.4.1-5
   ```
3. Соберите артефакты. ID ключа необязателен, но обязателен, если ключ закреплён:
   ```bash
   tools/make-release.sh v1.4.1-5 <GPG_KEY_ID>
   ```
4. Опубликуйте GitHub Release из тега. Он не должен быть черновиком или pre-release. Приложите файлы из `dist/<тег>/`:
   ```bash
   gh release create v1.4.1-5 dist/v1.4.1-5/* --title v1.4.1-5 --notes "..."
   ```
5. Проверьте из более старой установки: `crypTar --check-update`.

Требования к релизу:
- тег — это `v` + `VERSION` в формате SemVer;
- в `crypTar` сохранены строки `SRC_DIR="$SCRIPT_DIR/src"` и `VERSION="$(cat "$SCRIPT_DIR/VERSION")"`;
- `src/` содержит `utils/`, `lib/config.sh` и `commands/{encrypt,decrypt,send}.sh`.

По SemVer `1.4.1-5` старше `1.4.1-4`, но версия `1.4.1` без суффикса оказалась бы *старше* любой `1.4.1-N`. Используйте суффикс `-N` последовательно. Релизы, отмеченные как pre-release, пользователям не предлагаются. Если новому релизу нужны новые системные пакеты, перечислите их в описании релиза: `--update` системные пакеты не устанавливает.

### Запуск

Все тесты (файлы тестов имеют расширение `.sh`, поэтому перечислите их явно):
```bash
bats tests/*.sh
```

Один файл:
```bash
bats tests/test_config.sh
```

Тесты создают изолированный GPG-keyring во временной директории (`GNUPGHOME=$(mktemp -d)`) и не затрагивают реальный keyring разработчика. Облачные тесты и тесты обновления подменяют все HTTP-запросы — облачные аккаунты, токены и доступ в сеть не нужны; тесты `--update` заменяют `curl`, `sudo` и `git` заглушками и устанавливают программу во временный `HOME`. Тестам конфига нужен `flock` (util-linux), облачным — `jq`; при их отсутствии тесты пропускаются.

## Безопасность

- **Шифрование**: только асимметричное (GPG public key). Симметричные пароли не используются.
- **Учётные данные серверов**: хранятся в зашифрованном INI-файле (`~/.config/cryptar/`), доступном только владельцу (chmod 700).
- **Облачные учётные данные**: секреты OAuth-клиентов и токены хранятся только в зашифрованном GPG файле `clouds.conf.gpg` (`chmod 600`). CrypTar никогда не запрашивает пароли облачных аккаунтов (OAuth device flow) и запрашивает минимальные права (Google `drive.file`).
- **Никаких секретов в командной строке**: curl получает URL, заголовки, токен и тело запроса через файловый дескриптор конфигурации (`curl -K <(...)`), поэтому они не видны в выводе `ps`; значения конфига записываются только встроенными командами shell. Ссылки загрузки и адреса сессий обрабатываются так же.
- **Никаких секретов в логах**: сообщения об ошибках провайдеров проходят через фильтр маскировки; ответы с токенами, коды авторизации и заголовки не выводятся; трассировка (`set -x`) отключается внутри облачных команд.
- **Временные файлы**: создаются в `/dev/shm` (RAM-диск) при наличии, чтобы минимизировать время жизни расшифрованных данных на диске; HTTP-ответы (в которых могут быть токены) уничтожаются сразу после разбора.
- **sshpass**: пароль SSH передаётся через переменную среды `SSHPASS`, а не через аргументы командной строки (не виден в `ps aux`). Рекомендуется использовать аутентификацию по SSH-ключу.
- **Ротация ключей**: для смены GPG-ключа шифрования конфигов используйте `crypTar --server set-key` — он расшифрует конфиги серверов и облаков старым ключом и атомарно перешифрует новым. Чтобы отправить публичный ключ на удалённые серверы для расшифровки архивов — используйте `crypTar --server push-key`.
- **Переменные окружения**: `CRYPTAR_*_CLIENT_SECRET` удобны при настройке, но видны процессам того же пользователя; на общих машинах предпочтителен интерактивный ввод.
